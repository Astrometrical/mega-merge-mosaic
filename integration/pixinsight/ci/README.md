# PixInsight module CI build scripts

Per-platform drivers behind `.github/workflows/module.yml`'s three required
jobs (`linux-x64`, `macos-arm64`, `windows-x64`). Each job builds PCL from
pinned open-source, builds the module + worker, and runs `cargo test` (ipc
crates) + the host golden CTest suite — **no PixInsight install on the
runner, on any platform**. See
[`../../../docs/superpowers/specs/2026-07-28-pixinsight-ci-and-distribution-design.md`](../../../docs/superpowers/specs/2026-07-28-pixinsight-ci-and-distribution-design.md)
and
[`../../../docs/superpowers/specs/2026-07-29-pixinsight-winmac-ports-design.md`](../../../docs/superpowers/specs/2026-07-29-pixinsight-winmac-ports-design.md)
for the full design; this file documents what actually lives in this
directory.

## Layout

- `pcl-pin.env` — single source of truth for the pinned open-source PCL
  revision (`PCL_SHA`, `PCL_REPO_URL`, `PCL_VER_MAJOR/MINOR/RELEASE`). All six
  build scripts source it; bump it in one place to move the pin.
- `build-pcl.sh` / `build-pcl-macos.sh` / `build-pcl-windows.ps1` — fetch the
  pinned PCL commit, verify the SHA (hard gate) and `Version.cpp` (soft,
  warn-only check), and build the static PCL library for that platform:
  `libPCL-pxi.a` (Linux/macOS) or `PCL-pxi.lib` (Windows). The macOS and
  Windows scripts also build the six vendored 3rdparty static libs
  (`cminpack`, `lcms`, `lz4`, `RFC6234`, `zlib`, `zstd`) that the real PCL
  modules link against, using PCL's own per-platform 3rdparty driver
  (`src/3rdparty/macosx/make-3rdparty-arm64.sh`,
  `src\3rdparty\windows\make-3rdparty.bat`), and assert the full 7-archive
  closure landed before declaring success. All three publish `lib/` +
  `include/` to an `--out`/`-Out` prefix directory.
- `build-module-linux.sh` / `build-module-macos.sh` / `build-module-windows.ps1`
  — build the module (`mmm-pxm.so` / `.dylib` / `.dll`) + `mmm-ipc-worker`
  against a PCL prefix from the scripts above, enforce a warning-free build,
  verify the host transport objects actually linked in (no undefined
  `mmm::`/`_ZN3mmm` symbols), and stage `bin/{module,worker}` under a
  `--stage`/`-Stage` directory — the unsigned payload each CI job uploads as
  an artifact.
- `win/PCL.vcxproj` — see below.

## The pinned `win/PCL.vcxproj`

The pinned open-source PCL commit (`afea714e…`, PCL 2.10.4) ships Linux
(`src/pcl/linux/g++/makefile-x64`) and macOS
(`src/pcl/macosx/g++/makefile-arm64`) build trees, but **no Windows project**
— `src/pcl/windows/vc17/PCL.vcxproj` simply isn't in the upstream tree at
that SHA.

`win/PCL.vcxproj` is lifted from a local **licensed** PixInsight install
(`/opt/PixInsight/src/pcl/windows/vc17/PCL.vcxproj`), generated by the
PixInsight Makefile Generator v1.147 for PCL 2.10.4 — version-matched to the
pin in `pcl-pin.env`. It is self-contained: `StaticLibrary`, toolset `v143`,
`stdcpp20`, `/permissive- /Zc:__cplusplus`, AVX2/FMA,
`RuntimeLibrary=MultiThreadedDLL` (`/MD`), `TargetName=PCL-pxi`. It imports
only standard `Microsoft.Cpp.*` targets (no custom `.props` to also lift) and
references the core `..\..\*.cpp` sources by relative path, so it works once
dropped into a freshly fetched tree at `src/pcl/windows/vc17/`. Licensing
note: PCL build files are part of the open-source PCL distribution, so
pinning this generated project in-repo is consistent with that license — the
`.cpp`/`.h` sources it compiles still come from the fetched open-source
commit, never from the licensed install.

`build-pcl-windows.ps1` creates `src/pcl/windows/vc17/` in the fetched tree
(upstream omits the directory) and copies `win/PCL.vcxproj` into it before
running `msbuild`.

### Source-list drift guard

Because the pinned `.vcxproj` carries a **fixed** `<ClCompile>` list, a future
PCL pin bump could silently add or remove a `.cpp` in `src/pcl/` without the
Windows build noticing (Linux/macOS pick up new sources automatically via
their makefiles' globbing; the vcxproj can't). `build-pcl-windows.ps1` guards
against this: after fetching, it parses the `<ClCompile Include="…">` entries
out of the pinned project and diffs them against `src/pcl/*.cpp` in the
freshly fetched tree. Any file listed in the project but absent from the tree,
or present in the tree but not listed, fails the build loudly with the
specific filenames. At the current pin (`afea714e`, 2.10.4 both sides) this
is a no-op; it exists to catch drift the next time the pin moves.

## shm-name normalization contract

The IPC transport's shared-memory segment name is carried as a string inside
the JSON `Init` message — it's a **host↔worker wire contract**, not just an
OS API detail, so both sides must derive the identical name from the identical
input.

- POSIX (Linux/macOS) names use a leading slash, e.g. `/mmm-<session>-<n>`.
- Windows named file mappings live in a different namespace and forbid
  backslashes in the base name. Both the Rust `shm.rs` Windows path
  (`win_object_name` in `crates/mmm-core/src/ipc/shm.rs`) and the C++ host's
  Windows path (`win_object_name` in `mmm_shm.cpp`, see
  [`../host/README.md`](../host/README.md)) apply the **same** rule: strip a
  leading `/`, prefix `Local\` — `/mmm-foo` → `Local\mmm-foo`. Because the
  normalization is applied identically on both sides from the same input
  name, the name round-trips through the `Init` message unchanged in effect.
- **macOS caps POSIX shm object names at 31 characters** (`PSHMNAMLEN`).
  There's no separate macOS normalization step — the module's shm-name
  generator already keeps names short enough to fit under that limit on all
  platforms; if a future change grows the generated name, macOS is the
  platform that will fail first.

## Scope: CI-green is unsigned

All three CI jobs build **from source** and go green **without any code
signing**:

- **macOS**: a source-built binary carries no `com.apple.quarantine` xattr,
  so Gatekeeper does not gate the CI-spawned `mmm-ipc-worker`. Worker
  **notarization** matters only for a *downloaded/quarantined* worker at
  end-user install time and is a deferred follow-up — not implemented here.
- **Windows**: an unsigned spawned `.exe` runs fine; SmartScreen only warns
  on *download* of a distributed package, which CI doesn't do.
  **Authenticode / Azure Trusted Signing** is a deferred follow-up — not
  implemented here.
- **Module signing** (all platforms) is unrelated to CI and unchanged by this
  work: PixInsight ≥ 1.9 requires a signed module to *install*, but the only
  signer is the PixInsight binary itself, run on a licensed machine — see
  [`../module/README.md`](../module/README.md)'s "Code signing" section. CI
  never signs; it uploads unsigned artifacts that a maintainer signs locally
  before installing on a test machine.

Also out of scope / deferred (tracked in the winmac-ports design spec, not
CI gates): a macOS GUI smoke test (no Mac with a licensed PixInsight
available) and a Windows GUI smoke test (a **manual** maintainer step — see
[`../module/README.md`](../module/README.md)'s "Windows GUI validation
(manual)" section).
